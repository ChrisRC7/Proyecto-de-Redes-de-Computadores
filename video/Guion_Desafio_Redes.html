Problema y utilidad

0:35–2:00Diapositiva 2
En pantalla: Señalar primero el lado izquierdo y después las tres funcionalidades de la derecha.
Qué decir

En una red pequeña, configurar una interfaz desde la línea de comandos puede ser sencillo. El problema aparece cuando tenemos muchos equipos y debemos repetir los mismos cambios en cada uno. Esto consume tiempo y aumenta la posibilidad de cometer errores. Además, sin monitoreo podemos enterarnos tarde de que una interfaz dejó de funcionar.

Para atender este problema usamos RESTCONF, que permite consultar y modificar información del router mediante solicitudes HTTP. Los modelos YANG definen la estructura de esos datos, de manera que podemos trabajarlos desde aplicaciones y scripts.

Nuestra primera funcionalidad permite crear, modificar y eliminar interfaces. La segunda consulta su estado para identificar si alguna no está operativa. Y la tercera envía una alerta a Webex para informar al equipo encargado de la red.

Por ejemplo, un administrador puede aplicar cambios a varias interfaces, comprobar su estado y recibir una notificación cuando el monitoreo detecte una caída. Así buscamos reducir el trabajo repetitivo y facilitar una respuesta más oportuna.

Ahora Javier nos va a explicar qué recursos utilizamos y cómo se comunican entre sí.

Javier

Herramientas y requerimientos

2:00–3:00Diapositiva 3
En pantalla: Mostrar los cuatro bloques. Si se desea, indicar brevemente el cambio de sandbox.
Qué decir

Para implementar el caso de uso necesitamos cuatro elementos principales. Primero, un router virtual Cisco Catalyst 8000v con IOS XE 17.12. Como los sandboxes Always On presentaron problemas de disponibilidad, utilizamos un entorno bajo reserva de Cisco DevNet, al que accedimos mediante una VPN con OpenConnect.

En segundo lugar, usamos Postman para probar las solicitudes HTTP y Python para automatizarlas, con requests para RESTCONF y ncclient para NETCONF.

También usamos dos modelos YANG: ietf-interfaces, que describe las interfaces y su estado, e ietf-ip, que permite manejar su configuración IP.

Finalmente, creamos un bot y una sala de Webex para recibir las alertas. Necesitamos las credenciales del router y el token del bot, que se mantienen en la configuración local.

Javier

Arquitectura y flujo de comunicación

3:00–4:00Diapositiva 4
En pantalla: Recorrer el diagrama: PC → VPN → router; después PC → API Webex → sala.
Qué decir

En el diagrama vemos la computadora del operador, donde se ejecutan Postman y los scripts. Desde ahí nos conectamos por VPN a la red privada del sandbox.

RESTCONF utiliza HTTPS por el puerto 443; en nuestro caso intercambiamos datos en JSON siguiendo los modelos YANG. Como complemento, también probamos NETCONF, que usa SSH por el puerto 830 y mensajes XML.

El segundo flujo corresponde a Webex. Cuando el script consulta al router y detecta una interfaz caída, realiza otra solicitud HTTPS a la API de Webex. Así, el bot publica una alerta en la sala del equipo.

Webex no consulta directamente al router: es nuestro script el que conecta ambas APIs. Ahora Christopher va a demostrar cómo funciona la solución.

Christopher

Postman: configurar una interfaz

4:20–5:35Demostración · 1
En pantalla: Abrir colección y entorno preparados. Ocultar contraseñas y tokens. Mostrar método, URL, cuerpo y respuesta; ejecutar las peticiones seleccionadas.
Qué decir

En Postman tenemos una colección con las solicitudes del proyecto. Primero comprobamos la conexión mediante GET; esperamos un código 200.

Ahora usamos PUT para crear la Loopback500. En el cuerpo JSON indicamos su nombre, tipo y descripción. El código 201 indica que se creó un recurso nuevo. Con GET verificamos la interfaz creada.

Después utilizamos PATCH para modificar su descripción. El 204 indica una operación exitosa sin contenido de respuesta. Finalmente, con DELETE eliminamos la interfaz de prueba. Así podemos configurar el router directamente desde una API.

Apoyo para la demostración · No leer en voz alta
GET /restconf → 200
PUT .../interfaces/interface=Loopback500 → 201 (204 si ya existe)
GET .../interfaces/interface=Loopback500 → 200
PATCH .../interfaces/interface=Loopback500 → 204
DELETE .../interfaces/interface=Loopback500 → 204
Christopher

Python: configuración masiva

5:35–6:35Demostración · 2
En pantalla: Abrir terminal en caso-de-uso/ y mostrar interfaces.json (sin secretos). Ejecutar crear, listar y modificar. Dejar las interfaces creadas para la siguiente prueba.
Qué decir

Ahora automatizamos estas operaciones con Python. El archivo interfaces.json contiene el inventario de las interfaces que queremos gestionar.

Al ejecutar el script con la opción crear, se envían solicitudes PUT para las Loopback501, 502 y 503. En la salida podemos ver el código HTTP y el tiempo de cada operación. Con listar verificamos la configuración y con modificar cambiamos las descripciones de forma masiva.

La misma lógica puede reutilizarse con un inventario más grande. Además, el script guarda los resultados en archivos CSV.

Apoyo para la demostración · No leer en voz alta
python configurar_interfaces.py crear
python configurar_interfaces.py listar
python configurar_interfaces.py modificar --descripcion "CE5301 - modificada"

Monitoreo y alerta a Webex

6:35–7:55Demostración · 3
En pantalla: Mostrar estado inicial, apagar únicamente Loopback502, repetir monitoreo, mostrar mensaje nuevo en Webex. Recuperar y eliminar las interfaces de prueba al terminar.
Qué decir

Ahora comprobamos el monitoreo. El script consulta el estado de las interfaces; aquí vemos su estado administrativo y operativo.

Para simular una caída vamos a deshabilitar intencionalmente la Loopback502 mediante PATCH, cambiando enabled a false. Al repetir el monitoreo, la interfaz aparece como no operativa.

El script genera una alerta y la envía a la API de Webex. Esperamos un HTTP 200 y aquí podemos comprobar que el mensaje llegó a la sala con el nombre y estado de la interfaz.

La caída fue controlada, pero el mecanismo permite reportar interfaces no operativas. Para terminar, volvemos a habilitarla y borramos las interfaces de prueba.

Apoyo para la demostración · No leer en voz alta
python monitorear_interfaces.py --solo Loopback501 Loopback502 Loopback503
python configurar_interfaces.py apagar --solo Loopback502
python monitorear_interfaces.py --solo Loopback501 Loopback502 Loopback503
# Abrir la sala de Webex y verificar el mensaje nuevo.
python configurar_interfaces.py encender --solo Loopback502
python configurar_interfaces.py borrar --solo Loopback501 Loopback502 Loopback503
